3. ZERO-MATH INTUITION: CI/CD, QUALITY GATES & DVC EXPLAINED SIMPLY
================================================================================

Q: What is CI/CD in plain English?
A: Think of building software like assembling an airplane.
   - Traditional Software: You assemble all the parts over 6 months, turn the key, 
     and pray it flies. If it crashes, you don't know which of the 10,000 screws failed.
   - Continuous Integration (CI): Every time an engineer tightens a single screw (git commit), 
     an automated robot inspector immediately tests the torque, checks the metal alloy, 
     and runs a simulation. If anything fails, the assembly line stops instantly.
   - Continuous Deployment (CD): Once all robotic checks pass, the plane is automatically 
     fueled and placed on the runway for passengers.

Q: What is the difference between Unit Testing and Smoke Testing?
A: - Unit Testing (Stage 2) is testing the car battery on a test bench with a voltmeter. 
     You test isolated functions in memory.
   - Smoke Testing (Stage 4) is putting the battery in the car, turning the ignition, 
     and seeing if the engine starts without smoke coming out of the hood. You test the 
     fully assembled system in its real container environment.

Q: Why do we need DVC when we already have Git?
A: Git was built for plain text files (code). If you commit a 2 GB neural network or 
   500 MB dataset to Git, your repository becomes painfully slow to clone. DVC keeps small 
   text pointer files (.dvc) in Git and stores the massive binary models in cloud storage 
   (AWS S3, Google Cloud Storage), syncing them via cryptographic SHA-256 hashes.

5. COMPREHENSIVE VIVA VOCE Q&A (Top 18 Questions & Master Answers)
================================================================================

Q1: What is a GitHub Actions Workflow and what file format does it use?
A1: A workflow is an automated configurable process made up of one or more jobs. It is 
    declared in YAML syntax and stored under the .github/workflows/ directory in the repository.

Q2: What is the difference between an Event, a Job, and a Step in GitHub Actions?
A2: - Event: The trigger that starts a workflow (e.g., git push, pull_request, workflow_dispatch).
    - Job: A set of steps that execute on the same runner (e.g., lint, test, docker-build). 
      Jobs run in parallel unless sequential dependencies are declared using 'needs'.
    - Step: An individual task within a job, either running a shell command or invoking an action.

Q3: Why did you use 'needs: [lint]' between Stage 1 and Stage 2?
A3: To implement a fail-fast strategy. If code contains syntax errors or severe PEP 8 defects, 
    running unit tests or downloading dependencies wastes CPU minutes. By making tests depend 
    on linting, the pipeline halts immediately upon encountering code defects.

Q4: How does GitHub Actions manage dependency caching?
A4: Using actions/setup-python with cache: 'pip' or actions/cache@v4. It computes a cache key 
    based on the hash of requirements.txt. If dependencies have not changed, the runner restores 
    cached wheel files in seconds instead of re-downloading from PyPI.

Q5: What is the purpose of Flake8 and AST compilation in Stage 1?
A5: Python is an interpreted language; syntax errors are only discovered when that line is 
    executed. The Python AST (Abstract Syntax Tree) compiler parses all 44 source files 
    ahead-of-time without running them, guaranteeing 100% syntactic validity. Flake8 enforces 
    PEP 8 style rules, detecting undefined variables and unused imports.

Q6: What 4 categories of tests are evaluated in your Pytest suite?
A6: 1. Model Artifact Integrity: File existence, minimum file size, and .predict() interface.
    2. Endpoint Contracts: GET /, GET /health, POST /predict, and POST /predict/batch responses.
    3. Input Validation Error Boundaries: HTTP 422 Unprocessable Entity for empty or malformed text.
    4. Latency SLA Assertion: Strictly asserting response time stays below 150 milliseconds.

Q7: What is DVC and how does it fit into the CI/CD pipeline?
A7: DVC (Data Version Control) is an open-source tool that versions data and ML models alongside 
    Git. In CI/CD, Git tracks the small .dvc text file containing the SHA-256 hash. The runner 
    uses DVC to verify that the local model matches the exact cryptographic hash approved by 
    the data science team before deploying.

Q8: How did you verify the model integrity in Stage 3?
A8: We verified that the model file exists, is over 100 KB (actual size: 2.44 MB), matches its 
    expected SHA-256 hash (efacfe2e9ca...), and unpickles cleanly into an object implementing .predict().

Q9: What is a container smoke test and why is it necessary?
A9: A smoke test is a preliminary test that reveals simple failures severe enough to reject a release. 
    Even if code passes unit tests on the host, differences in OS shared libraries (e.g., libgomp 
    for LightGBM) can crash the container. The smoke test builds the real Docker image, launches it, 
    and issues curl requests to /health and /predict to prove runtime viability.

Q10: What happens if a step fails in GitHub Actions?
A10: By default, if any step returns a non-zero exit code, the job fails immediately, downstream 
     jobs marked with 'needs' are cancelled, the commit is flagged with a red cross (❌), and 
     pull request merge buttons are blocked.

Q11: How do you prevent breaking changes from reaching production?
A11: By configuring GitHub Branch Protection Rules on the 'main' branch:
     1. Require status checks to pass before merging (all 4 CI jobs must be green).
     2. Require pull request reviews (at least 1 peer approval).
     3. Require linear history and dismiss stale approvals on new commits.

Q12: Compare GitHub Actions, GitLab CI, and Jenkins.
A12: - GitHub Actions: Best for GitHub repositories; zero server management; managed cloud runners; 
       native secret management.
     - GitLab CI: Excellent built-in container registry and Kubernetes cluster integration via 
       .gitlab-ci.yml; requires self-managed runners for on-premise GPU nodes.
     - Jenkins: Older, highly customizable via plugins, but requires dedicated server management, 
       complex Groovy pipeline scripts, and high maintenance overhead.

Q13: What is the difference between Continuous Delivery and Continuous Deployment?
A13: - Continuous Delivery: Every change that passes CI is built, tested, and staged in a releasable 
       artifact (e.g., container image tagged in registry), requiring human approval to deploy to production.
     - Continuous Deployment: Every change that passes all CI/CD gates is automatically released to 
       production users with zero human intervention.

Q14: What is Blue-Green Deployment and how does it prevent downtime?
A14: Blue-Green deployment runs two identical production environments: Blue (currently serving live traffic) 
     and Green (idle). The CD pipeline deploys the new container image to Green, runs healthchecks 
     and smoke tests. Once verified, the load balancer router instantly switches traffic from Blue to Green. 
     If an issue arises, traffic immediately switches back to Blue.

Q15: What is Canary Deployment?
A15: Canary deployment routes a tiny fraction of real user traffic (e.g., 5%) to the newly deployed 
     container while 95% remains on the stable version. The system monitors error rates and latency. 
     If telemetry remains healthy, traffic gradually shifts to 100%.

Q16: How do you handle sensitive credentials (e.g., Docker Hub tokens, AWS keys) in GitHub Actions?
A16: Credentials are never hardcoded in YAML files. They are encrypted and stored in GitHub Repository 
     Secrets (Settings -> Secrets and variables -> Actions). In the workflow, they are injected securely 
     as environment variables using secrets.DOCKER_PASSWORD.

Q17: What is Continuous Training (CT) in MLOps?
A17: Beyond CI and CD, Continuous Training (CT) automatically retrains and validates new model versions 
     when incoming production data drifts or new training labels are committed via DVC.

Q18: What exit code indicates success in shell scripts and CI runners?
A18: Exit code 0 indicates success. Any non-zero exit code (1 to 255) signals an error or failure 
     that halts the pipeline.

6. REAL-WORLD PRODUCTION MLOPS & CLOUD ARCHITECTURE
================================================================================
In enterprise environments, Experiment 7 represents the core engine of an automated MLOps platform:

1. Code Repository (GitHub)
   ├── Pull Request Trigger -> Runs Linting, Pytest, DVC Checksum & Smoke Test
   └── Merge to main -> Tags Docker Image and pushes to GitHub Container Registry (ghcr.io)

2. Kubernetes Cluster (EKS / GKE)
   ├── Ingress Controller (NGINX / Envoy) routes traffic with TLS termination
   ├── Horizontal Pod Autoscaler (HPA) scales pods based on CPU utilization and request volume
   └── Automated Rollout -> Performs rolling update with zero user downtime

3. Observability & Telemetry
   ├── Prometheus polls /health and Prometheus metrics endpoint every 15s
   ├── Grafana displays real-time latency percentiles (p50, p95, p99) and error rates
   └── PagerDuty alerts engineering teams if error rate exceeds 0.5%
